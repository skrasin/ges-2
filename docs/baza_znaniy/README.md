# ГЭС-2 · База знаний служб взаимодействия с посетителями

Этот файл — техническое задание для Claude Code. Данные лежат в `ges2_kb_data.json`
(84 записи: 50 с готовым ответом, 34 — с открытым вопросом, ожидающим ответа от
профильных команд). Схема каждой записи описана в `meta.field_notes` внутри
самого JSON — прочитай её перед тем, как писать код.

## Контекст

Дом культуры «ГЭС-2» (музей, концертная площадка и мастерские в одном здании)
собирает базу знаний для сотрудников, которые общаются с посетителями:
на входе, на инфостойке, в залах, по телефону и по email. База знаний — это
готовые формулировки ответов на типовые вопросы посетителей, сгруппированные
по темам и категориям мероприятий.

## Что нужно сделать

Собери из `ges2_kb_data.json` рабочий инструмент для этой команды. Конкретную
реализацию выбирай сам исходя из простоты поддержки — ниже не жёсткая
спецификация, а ориентиры.

1. **Хранилище**: можно оставить JSON как источник правды, либо перенести в
   SQLite/аналог, если понадобится полнотекстовый поиск или фильтрация —
   решай по объёму (84 записи сейчас, но `pending`-записи будут пополняться).
2. **Поиск и фильтрация**: сотруднику нужно быстро найти ответ по ключевым
   словам из вопроса посетителя и/или отфильтровать по `category`. Полезно
   отдельно выводить список `status = pending`, чтобы им могла заниматься
   команда, ответственная за заполнение.
3. **Формат отдачи**: решай сам — CLI-поиск, простая локальная веб-страница
   или markdown-экспорт для вставки в Notion/Confluence. Учитывай, что
   конечные пользователи — не разработчики, поэтому интерфейс поиска должен
   быть проще, чем работа с сырым JSON.
4. **Workflow для `pending`-записей**: нужен понятный способ дозаполнять
   `answer`, проставлять `source` и `last_updated`, не ломая `id` записи —
   на эти `id` могут ссылаться извне (например, из скриптов по каналам).
5. **Валидация данных**: при любых изменениях схемы проверяй, что у каждой
   записи с `status: "answered"` заполнены `answer` и `source`, а у записи с
   `status: "pending"` — `answer` пустой. Это единственное жёсткое правило
   целостности данных.

## Важно не потерять при доработке

- Плейсхолдеры `notes` у `pending`-записей — это не мусор, а объяснение,
  какой именно факт нужно найти и куда за ним обращаться. Не удаляй их при
  автозаполнении, пока запись не станет `answered`.
- Часть ответов зависит от конкретного мероприятия (хронометраж, возрастная
  маркировка) и намеренно не унифицирована — в `answer` для таких вопросов
  стоит текст вида «зависит от события, смотреть страницу в календаре». Не
  пытайся угадать за пользователя точные цифры при доработке контента.
- `channels` сейчас одинаковы для всех записей (ответы канало-независимые).
  Если в будущем понадобится дифференцировать по каналу — это отдельная
  задача, не переусложняй текущую структуру заранее.
